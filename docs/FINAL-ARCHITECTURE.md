# 最终版设计：从「通用最优」到「你的角色池里的最优」（2026-11-09）

> 用户的澄清是本项目最重要的产品修正：
> **「没有什么最优解，是需要玩家当前的角色池来判定。」**
> 此前所有"最优配队"都是假设全角色，对真实玩家只是参考；最终版必须**以玩家实际拥有的角色为输入**。

## 一、为什么要改（审计）

| 现状 | 问题 |
|---|---|
| `TeamSolver.LoadPool(seasonElements)` 默认全角色 | 配队可能给出玩家一个都没有的角色 |
| 已有 `rosterNames` 过滤 + `PoolFull=false` 标记 | 但**玩家不会手填 GOOD 文件**，实际几乎总是空池 |
| 量化评分 `Confidence` 在无池时会降级 | 降级了，但**指示仍然基于不存在的角色** |
| `CuratedPicks` / `CharacterStrength` 都依赖池 | 池为空时强度全 -1、推荐无意义 |

结论：**缺的不是算法，是"自动拿到玩家角色池"这一步**。没有它，"个性化"永远停在纸面。

## 二、获取角色池：五种方案的审计

| 方案 | 完整性 | 合规（红线） | 自动化 | 结论 |
|---|---|---|---|---|
| **A. Enka.Network API**（UID 查角色展柜） | 命座/天赋/武器/圣遗物**全有** | ✅ 只读公开 API，不碰游戏进程 | ✅ 开游戏+展柜即可 | **主方案** |
| B. 游戏日志抽卡记录 | 只有"抽到过"，无圣遗物/命座 | ✅ 只读文件 | ✅ | 备选（补全"可能拥有"） |
| C. OCR 扫角色界面 | 角色名/等级 | ✅ 本进程截图 | 半自动 | **离线兜底**（复用已有 `--roster-scan`） |
| D. GOOD 文件（胡桃/扫描器导出） | 全有 | ✅ | ❌ 需玩家操作 | 精确保底 |
| E. 读游戏内存 | 全有 | ❌ **违反封号红线** | — | **禁止** |

**关于「照抄胡桃工具箱」**：Hutao 的角色/武器/圣遗物详情走的正是 **Enka.Network**（社区标准公开接口），
不是读内存。所以"照抄"的正确含义是**采用同一个数据源与同样的字段映射**，而不是复制它的注入/内存代码。

> 环境说明：本轮审计时 Hutao 仓库（`DGP-Studio/Snap.Hutao`）返回 404（可能已归档/迁移），
> 无法直接比对源码；但 Enka 的字段语义是公开的，可按接口实测对齐。

## 三、架构：三层角色池来源（与项目既有的多级兜底一致）

```
            ┌──────────────────────────────────────────┐
            │ RosterResolver（统一入口，按优先级尝试）    │
            └───────────────┬──────────────────────────┘
                            │
      ┌─────────────────────┼─────────────────────┐
      ▼                     ▼                     ▼
 ① Enka(UID)          ② OCR 扫角色界面        ③ GOOD 文件
   完整、自动             离线可用、角色名/等级      精确、需玩家导出
      │                     │                     │
      └─────────────────────┴─────────────────────┘
                            ▼
                  RolePool { owned[], source, confidence }
                            ▼
        TeamSolver / QuantScorer / CuratedPicks / CharacterStrength
                            ▼
              「你有的角色里」的最优配队与逐幕指示
```

**关键原则**（承袭项目已有设计）：
1. **来源必须写进 `Provenance`**——玩家要能看出"这个建议是基于 Enka 数据 / OCR 猜的 / 你以为我全有"；
2. **缺数据就明说**，不假装：池不完整时 `Confidence` 降级并提示"补全角色池后更准"；
3. **任何来源失败都回退**到下一层，不阻塞主链路。

## 四、Enka 字段 → GOOD 映射（决定角色强度能否算）

| Enka 字段 | 我们的用法 | 说明 |
|---|---|---|
| `avatarInfoList[].avatarId` | → `characters[].key` | 需 id→英文名映射表 |
| `avatarInfoList[].skillLevelMap` | → `talent{auto,skill,burst}` | 天赋等级 |
| `avatarInfoList[].talentIdList` | → `constellation = len-1` | 命座数 |
| `avatarInfoList[].equipList[]` | 武器 + 圣遗物 | 需区分 `weapon` 与 `reliquary` |
| `flat.props` | 圣遗物主属性/等级 | 用于 CV 与有效词条 |

**这是全链路的关键**：能拿到这些，`CharacterStrength`（圣遗物 CV/词条/天赋/命座/武器精炼）
就能真的算出来，而不是只在演示样本上算。

## 五、对"最优解"的重新定义（产品口径）

| 旧口径 | 新口径（最终版） |
|---|---|
| "第6幕最优 = 五郎/九条裟罗/伊安珊" | "**在你拥有的角色里**，第6幕最稳的是 X/Y/Z；缺 Z 时可用 A 代替" |
| 只给一个答案 | 给**主方案 + 备选方案 + 缺口提示**（"你缺少破盾角色，建议练 X"） |
| 置信度只反映数据完整度 | 置信度同时反映**池覆盖度**：池越小，越明确说"这是在你现有角色下的最优" |

对应实现要点：
- `TeamSolver` 评分不变，但**输入池来自玩家**；
- 输出增加"**缺口 → 可练角色**"建议（用 `substitutes.json` + 全角色池反查）；
- 幕级推荐（`CuratedPicks` + 新 `act-teams.json`）标注"你池里有/没有"。

## 七、需要你确认的两点

1. **UID 是否可以提供**（Enka 只读公开展柜，需要你在游戏里把角色放进"角色展柜"）；
2. 若不便用 Enka，是否接受**先用 OCR 扫一遍角色界面**（准确率有限，但完全离线）作为初始池，
   之后再用 GOOD 文件补精？
